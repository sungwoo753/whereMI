# PR 요약 작성

브랜치의 커밋들을 읽고 "무엇을, 왜 바꿨는지"를 리뷰어가 1분 안에 파악할 수 있는 PR 제목과 본문으로 정리한다.
커밋 메시지를 나열하는 게 아니라, 실제 diff 를 보고 변경을 기능 단위로 묶어 설명하는 것이 핵심이다.
커밋 메시지는 작성 당시의 의도일 뿐이고, 여러 커밋에 걸쳐 고쳐지거나 되돌려진 내용은 최종 diff 기준으로 써야 리뷰어가 헷갈리지 않는다.

## 1. 재료 모으기

```bash
bash .claude/skills/pr-summary/scripts/collect.sh [base]
```

기준 브랜치를 사용자가 말하지 않으면 생략한다 (저장소 기본 브랜치 → origin/HEAD → main 순으로 자동 결정).
출력에는 브랜치 정보, 커밋 전체 메시지, 변경 파일 통계, 코드 diff(이미지·바이너리 제외, 길면 잘림), 기존 PR 여부가 들어 있다.

- diff 가 잘렸으면 중요한 파일만 `git diff <merge-base>..HEAD -- <path>` 로 더 읽는다. 전부 다 읽으려 하지 말고, 통계에서 변경량이 큰 파일과 핵심 로직 파일 위주로 본다.
- 커밋되지 않은 변경이 있으면 PR 에 포함되지 않는다고 사용자에게 한 줄 알려 준다.
- 커밋이 0개면 PR 로 올릴 게 없다고 말하고 멈춘다.
- `gh` 는 출력의 `gh:` 줄에 찍힌 경로를 쓴다. 이 PC 에서는 PATH 의 `gh` 가 다른 도구일 수 있다.

## 2. 이해하고 묶기

- 변경을 **기능/영역 단위**로 묶는다 (예: 열차 추적 로직, 위젯 UI, 알림, 루틴, 빌드 설정). 파일 단위나 커밋 단위로 나열하지 않는다.
- 각 묶음마다 "무엇이 바뀌었고 사용자/동작 관점에서 무엇이 달라지는지"를 쓴다. 왜 그렇게 했는지가 커밋이나 코드 주석에 드러나면 함께 쓴다.
- 중간 커밋에서 생겼다가 이후 커밋에서 없어진 것은 쓰지 않는다. 최종 상태만 설명한다.
- 테스트 파일 변경, 권한/매니페스트 변경, 외부 API 호출량, 의존성 추가, 설정 파일 변경처럼 리뷰어가 놓치기 쉬운 위험 요소는 따로 모아 둔다.

## 3. 쓰기

제목: 한국어, 50자 안팎, 이 PR 의 가장 큰 변화를 한 문장으로. 접두사(feat: 등)는 저장소 커밋이 그런 규칙을 쓸 때만 따른다.

본문은 아래 틀을 쓴다. 해당 내용이 없는 섹션은 통째로 뺀다 (빈 섹션이나 "없음"을 남기지 않는다).

```markdown
## 요약
<이 PR 이 하는 일을 2~3문장. 배경이 있으면 한 줄 포함>

## 주요 변경사항
### <기능/영역 1>
- <변경 내용과 그로 인한 동작 변화>
### <기능/영역 2>
- ...

## 테스트
- <단위 테스트: 추가/수정된 테스트와 무엇을 검증하는지. 실행 결과를 이 세션에서 확인했다면 결과 숫자>
- <실기기/수동 확인 여부. 확인 안 한 것은 확인 안 했다고 쓴다>

## 리뷰 포인트
- <권한, 외부 API, 의존성, 데이터 저장 형식, 되돌리기 어려운 변경 등 주의해서 볼 곳>

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

작성 원칙:
- 리뷰어 기준의 쉬운 한국어로 쓴다. 클래스/함수 이름은 처음 나올 때 백틱으로 감싸고 역할을 짧게 붙인다.
- 테스트를 실제로 돌리지 않았다면 통과했다고 쓰지 않는다. 원하면 이 단계에서 프로젝트의 테스트 명령을 돌려 결과를 넣는다 (예: Android 면 `./gradlew testDebugUnitTest`, 로컬 Gradle 경로가 따로 있으면 그것).
- 비밀값(API 키, 토큰)이나 개인 정보가 diff 에 보이면 본문에 옮기지 말고 사용자에게 경고한다.

## 4. 확인받고 반영하기

1. 제목과 본문 초안을 사용자에게 보여 준다. 그리고 어떤 동작을 할지 한 줄로 말한다:
   - 기존 PR 이 열려 있으면: "PR #N 의 제목·본문을 이 내용으로 바꿀게요"
   - 없으면: "<head> → <base> PR 을 새로 만들게요"
2. 사용자가 확인하면 본문을 임시 파일에 저장하고 반영한다. (따옴표·줄바꿈이 깨지지 않도록 `--body-file` 을 쓴다)
   ```bash
   # 기존 PR 갱신
   <gh> pr edit <number> --title "<제목>" --body-file <임시파일>
   # 새 PR
   <gh> pr create --base <base> --head <head> --title "<제목>" --body-file <임시파일>
   ```
   브랜치가 아직 원격에 없으면 `git push -u origin <head>` 가 먼저 필요하다. push 도 원격에 올리는 일이므로 사용자 확인에 포함해서 묻는다.
3. 반영 후 PR URL 을 알려 준다.

사용자가 "초안만" 이라고 하면 1번에서 멈춘다. GitHub 에 반영하는 것은 다른 사람에게도 보이는 일이라, 사용자가 명시적으로 바로 하라고 한 경우가 아니면 반드시 초안을 먼저 보여 준다.
